## 1. Executive Summary and Architectural Principles

The **OVIC EON ROS 2 Integration Architecture** defines the bridge between EON's emotional intelligence infrastructure and the standard Robot Operating System 2 (ROS 2) middleware ecosystem.

Crucially, this integration adheres to three architectural invariants:
1. **Zero Mandatory Dependency on ROS 2:** EON Core and the C++ / Python SDKs remain completely decoupled from ROS 2. EON runs as a standalone daemon in non-ROS environments. The ROS 2 capability is delivered via an optional, standalone package: `eon_ros2_bridge`.
2. **Strict Managed Lifecycle Integration:** EON ROS 2 nodes implement standard `rclcpp_lifecycle::LifecycleNode` contracts, guaranteeing deterministic state coordination with host robot launch files and navigation state managers.
3. **Non-Authoritative Motion Boundary:** Outputs generated by EON (such as gaze tracking, gesture suggestions, or social approach recommendations) are strictly formatted as non-authoritative proposals (`is_authoritative = false`). The robot's primary safety controller, collision avoidance layer (e.g., Nav2 costmaps), and hardware emergency stops retain 100% final authority.

## 3. Node Decomposition and Responsibilities

The bridge consists of modular, composable lifecycle nodes that can be launched individually or composed into a single process container (`rclcpp_components`):

1. **`eon_sensor_bridge_node`:** Subscribes to standard ROS 2 perceptual topics (`sensor_msgs/msg/Image`, audio chunks, TF frames) and pushes them into EON Core via `libeonsdk` zero-copy shared memory.
2. **`eon_engine_monitor_node`:** Queries EON Core operational health and publishes standard ROS 2 diagnostics (`diagnostic_msgs/msg/DiagnosticArray`) and heartbeat signals.
3. **`eon_social_response_bridge_node`:** Listens for EON Emotion Response Generation (`ERG`) events and translates them into ROS 2 topic proposals and Action servers for robot interaction.

## 4. Multi-Robot Namespacing and Discovery Isolation

In fleet deployments with multiple interacting robots:
- Each robot instantiates the bridge under a specific root namespace (e.g., `/robot_01/eon/...`, `/robot_02/eon/...`).
- DDS domain IDs (`ROS_DOMAIN_ID`) or Zenoh DDS routers provide transport isolation between robots.
- Inter-robot social communication takes place only via high-level EON context events, preventing raw sensor flooding across the wireless network.
